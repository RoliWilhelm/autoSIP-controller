(a) Does the workflow exist as described?
-----------------------------------------
YES, with one precision: the position-capture only happens on the FIRST
Return-to-Origin click within a given pause. Subsequent clicks during the
same pause re-drive to (0, 0) and re-tare but do NOT overwrite the captured
reference (gate at main.py:4381 — `if s.is_paused and not
s.origin_returned_during_pause`). This means an operator who re-parks
imperfectly and clicks Return-to-Origin again will still land on the
ORIGINAL paused-position reference on Resume.

Workflow as observed in code (chronological):
  1. State machine reaches a phase that can be paused (pump / wait / move
     / discard).
  2. Operator clicks Pause. `state.is_paused = True`.
  3. Operator clicks Return to Origin.
     - First click in this pause: captures
         state.paused_table_cm    = current table motor angle × cm/deg
         state.paused_carriage_cm = current carriage motor angle × cm/deg
       and sets state.origin_returned_during_pause = True.
     - Then drives both motors to (0, 0) cm and tares the angle counters,
       so (0, 0) cm now corresponds to wherever the carriage was when the
       move command was issued.
  4. (Optional) Operator physically re-parks the carriage against the
     orientation-appropriate mechanical-limit corner to true-up against
     stepper drift.
  5. Operator clicks Resume.


(b) Precise trigger point for the calibration dialog
----------------------------------------------------
The dialog opens AFTER Resume, AFTER the motors have driven back to the
captured paused position — NOT immediately when Return to Origin is
clicked.

Exact sequence inside App.toggle_pause's Resume branch (main.py:5448):
  1. Resume-branch entry: detects state.origin_returned_during_pause.
  2. Status update: "Returning to paused position…".
  3. move_to_positions(table_dist=state.paused_table_cm,
                       carriage_dist=state.paused_carriage_cm,
                       is_transit=True)
     — synchronous, blocks the GUI until the carriage physically lands.
  4. THEN calls _show_calibration_confirm_dialog(paused_x_cm,
     paused_y_cm). The dialog is grab_set() modal and waits.
  5. On Confirm: clears state.origin_returned_during_pause, sets status
     "Fractionation in progress...", resumes the elapsed clock, drops a
     resume-breadcrumb row in log.csv (collect phase), and re-arms the
     state machine from the previous (state.state) of pump / wait / move.
  6. On Cancel: state.is_paused is re-set to True, status reads
     "Calibration not confirmed. Run remains paused.", and the run
     remains paused. The capture flag stays True so the operator can
     re-park and click Resume again to retry.

Implication for the manuscript: the dialog DOES NOT appear at the moment
of the Return-to-Origin click. The operator has time between click and
Resume to manually re-park; the dialog is the "I'm back at the paused
position — confirm calibration before I dispense the next well" check.

(a) What does Manual-mode Return to Origin actually do?
-------------------------------------------------------
Two actions, in this order (main.py:2426):

  1. `self.app.carriage_return()` — drives BOTH motors to (0, 0) cm
     absolute (move_dist_absolute(0.0, is_transit=True) on each axis).
  2. `self.app.table_motor.tare()` and `self.app.carriage_motor.tare()`
     — set the software's angle counters to 0.
  3. `self.refresh_position_readout()` — updates the Position label so
     it reads "X = 0.00 cm, Y = 0.00 cm".

The tare runs IMMEDIATELY after the move, as part of the same click
handler. There is no in-handler pause waiting for a manual re-park;
the operator's re-park is a separate action they perform afterwards.

Consequence: the documented physical recalibration loop is

  Click Return to Origin → motors drive to (0, 0), motors release, tare → 
  operator manually slides the carriage to the true mechanical-limit corner → 
  click Return to Origin AGAIN to re-zero against the now-correct position.

The second click is what makes the tared origin equal the mechanical
limit. The handler does not enforce this — it's the standard "click
after re-park" pattern.


(b) Is there a "return to last visited well" step in Manual mode?
-----------------------------------------------------------------
No. Manual mode has no concept of an "active automated run", and
_home_clicked does not consult state.x / state.y or any captured
paused-position fields. The function performs the move-to-(0, 0) +
tare pair and stops. No subsequent re-position step exists in the
Manual code path.

(d) Conclusion: is the manuscript claim accurate?
--------------------------------------------------
The claim "This same calibration can be performed in the Manual Mode
when an automated fractionation session is not underway." is
INACCURATE as written. Manual mode supports only the PHYSICAL portion
of the calibration; it does NOT replicate the full Automated-Resume
loop.

What Manual mode DOES support:
  • Return to Origin button (Manual mode's "Return to Origin", handler
    _home_clicked). Drives motors to (0, 0) and tares.
  • Operator can manually re-park the carriage against the
    orientation-appropriate mechanical-limit corner after the move.
  • Click Return to Origin a SECOND time to re-tare against the
    re-parked physical position. The Position readout then shows
    `X = 0.00 cm, Y = 0.00 cm` against the corrected origin.

What Manual mode does NOT do:
  • Manual mode has no captured "last visited well" — no automated
    run is active, so there is no last-well state to return to.
  • No automatic move-back step after the operator clicks Return
    to Origin. The carriage stays wherever the operator left it.
  • No Origin Calibration confirmation dialog. That dialog is
    exclusive to the Automated mid-pause → Resume path.

Suggested rewording for the manuscript:
  "The PHYSICAL recalibration step — drive to origin, re-park, re-zero
  — can also be performed in Manual mode when no automated run is
  underway: click Return to Origin, manually re-park, then click
  Return to Origin again to re-tare. Manual mode has no last-visited
  well to return to and does not pop the Origin Calibration
  confirmation dialog; those are Resume-after-pause behaviors of
  Automated mode."


(e) Order of operations during a mid-pause recalibration
--------------------------------------------------------
Chronological sequence in the code (verified by following
return_to_origin → toggle_pause Resume branch):

  Click Return to Origin during pause:
    1. `App.return_to_origin` captures (paused_table_cm,
       paused_carriage_cm) from the live motor angles — but ONLY on
       the FIRST click in this pause (gated by
       `not s.origin_returned_during_pause`, set True after capture).
    2. `App.carriage_return()` drives both motors to (0, 0) cm absolute.
    3. `table_motor.tare()` and `carriage_motor.tare()` zero the
       software angle counters.
    4. Status: "Returned to origin. Manually re-park the carriage
       against the {origin} limit, then click Resume."

  Operator action (NOT captured by the software):
    5. Operator physically slides the carriage to the mechanical-limit
       corner. The motors were released after the previous move
       (StepperMotor.release in move_relative — for overheating
       prevention), so the operator can push the carriage by hand and
       the angle counters stay at 0.

  Click Resume:
    6. `App.toggle_pause` Resume branch detects
       `s.origin_returned_during_pause == True`.
    7. Status: "Returning to paused position…".
    8. `move_to_positions(table_dist=s.paused_table_cm,
                          carriage_dist=s.paused_carriage_cm,
                          is_transit=True)` — drives BOTH motors to
       the captured paused position. Synchronous; blocks until the
       motors physically arrive.
    9. `_show_origin_calibration_dialog(paused_x_cm, paused_y_cm)`
       opens, asks the operator to verify the needle is over the
       expected well.
   10. On Confirm: clears the flag, resumes the state machine from
       the previous pump / wait / move state.
       On Cancel: leaves the flag True, sets state.is_paused = True,
       leaves the carriage at the captured paused position so the
       operator can manually re-park and click Resume again.

Critical clarification on the tare:
  The TARE itself happens inside `App.return_to_origin` (step 3), 
  BEFORE the operator manually re-parks. The manuscript's description
  that "the tare happens after the manual re-park" is chronologically
  inaccurate.

  Why the loop still works: the steppers release their coils after
  every commanded move (StepperMotor.release at the end of
  move_relative — prevents overheating), so when the operator pushes
  the carriage by hand in step 5, the motor angles DO NOT update.
  The tared angle counter of 0 therefore ends up associated with the
  manually re-parked physical position. On Resume, the software issues
  `move_dist_absolute(s.paused_table_cm)` from this corrected origin,
  and the carriage lands at the TRUE paused-position coordinates
  relative to the freshly re-parked mechanical limit.

  Functionally the manuscript is correct: the manually re-parked
  position becomes the new software origin. Chronologically it is
  wrong: the tare action is performed by the Return to Origin click,
  not by Resume.

Suggested manuscript wording:
  "Return to Origin drives the motors to the software origin and
  immediately tares the angle counters; the operator then manually
  re-parks the carriage against the mechanical-limit corner — because
  the motors are released between moves, the manual push silently
  re-locates the (already-tared) software origin to the true mechanical
  limit. On Resume the software drives the syringe head from this
  corrected origin to the last visited well's coordinates, then opens
  the Origin Calibration dialog so the operator can verify the needle
  landed where expected before fractionation resumes."
